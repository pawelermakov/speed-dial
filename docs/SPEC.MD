# SPEC: Полный перенос SpeedDial X на WXT + Vue 3 + TypeScript + Tailwind CSS 4

> **Адресат:** Codex, запущенный в корне существующего репозитория `speed-dial`.
> **Статус:** исполняемая спецификация; требуется выполнить **весь перенос функциональности**, а не только создать каркас WXT.
> **Язык интерфейса и документации:** русский. **Язык исходного кода:** TypeScript/Vue; имена сущностей и Conventional Commits — английский.
> **Приоритеты:** сохранность данных → полнота функциональности → Chrome/Firefox → простота и читаемость → визуальная близость → необязательные оптимизации.

## 0. Задача и границы

Перепиши существующее расширение **SpeedDial X** на основе **официального Vue-стартера WXT** с **Vue 3, Composition API, `<script setup lang="ts">`, TypeScript и Tailwind CSS 4**. Сохрани всё пользовательское поведение, доступное в старом коде, кроме подтверждённо неработающих/небезопасных технических деталей, которые нужно заменить эквивалентами. Обеспечь отдельные сборки и работоспособность **Google Chrome и Mozilla Firefox**.

Это **миграция существующего продукта**, а не разработка похожего speed-dial с нуля. Не заменяй поиск Яндекса другим поисковиком, не убирай уведомления Mail.ru, не заменяй скриншоты одними favicon, не пропускай импорт/экспорт, настройки или контекстное меню. Не добавляй до завершения миграции папки закладок, синхронизацию, виджеты, тему оформления, новые поисковые системы, аналитику, регистрацию или другие новые функции. Не создавай popup/options/content scripts без объективной необходимости: основной UI — **страница новой вкладки**.

**Целевое состояние:** полностью работающая новая вкладка со старым набором функций, чистой структурой Vue, сохраняемыми данными, тестами, инструкциями сборки и документированными ограничениями. Последняя секция этого файла содержит проверяемый Definition of Done. Не останавливайся после `wxt init`; выполняй все этапы последовательно, самостоятельно исправляя возникающие ошибки и документируя неподтверждённые браузерные сценарии.

## 1. Git и безопасность изменений

**Желаемая итоговая модель:**

- `legacy` — самостоятельная ветка с неизменённой старой реализацией (без перемещения в `legacy/`).
- `main` — новая реализация на WXT, со **всей прежней историей коммитов**.
- Файл **`SPEC.MD` остаётся в корне `main`**. В итоговом приложении нет постоянно хранимой копии старого приложения.
- Не создавай новый Git-репозиторий, не удаляй `.git`, не используй `git init` внутри текущего репозитория, не переписывай историю `main` и не выполняй force-push.

Алгоритм:

1. Убедись, что запущен именно корень `speed-dial` (`git rev-parse --show-toplevel`, `git status`, `git branch -a`). Проверь наличие пользовательских несохранённых/неотслеживаемых файлов. **Ничего не перезаписывай и не удаляй без проверки**; появление только этого `SPEC.MD` как неотслеживаемого файла допустимо.
2. Убедись, что `main` указывает на старое приложение. Если ветки `legacy` нет — создай `git branch legacy main` **до удаления старых исходников**. Если есть, убедись, что она действительно соответствует исходной версии; не передвигай и не перезаписывай её автоматически.
3. Для доступа к старому коду используй `git show legacy:<path>` или, при удобстве, **Git Worktree** в соседней директории: `git worktree add ../speed-dial-legacy legacy`. Не копируй старую версию в `main/legacy`.
4. Работай в `main`. Если `main` содержит чужие незакоммиченные правки, которые могут пострадать, сначала безопасно сохрани их/сообщи о блокере — **не применяй** `git reset --hard`, `git clean -fd`, массовые удаления без инвентаризации.
5. Разрешены разумные локальные коммиты после завершённых этапов в формате **Conventional Commits без scope**, например `chore: initialize WXT project`, `feat: migrate bookmark storage`, `feat: restore screenshot capture`, `test: cover legacy import`. Коммить только собственные изменения; `SPEC.MD` не удаляй.
6. **Не выполняй `git push`, создание релиза/тега, публикацию расширения и автослияние без явного разрешения пользователя.** Если Git-коммиты невозможны, не маскируй проблему: оставь рабочие файлы и дай точный отчёт.
7. Старую версию можно сопоставлять визуально и по коду, но её нельзя считать рабочей в современном браузере: Web SQL удалён (см. §4).

При создании WXT **не запускай `wxt init` поверх непустого корня**, если это может затереть файлы. Безопасный сценарий: создать официальный проект во временной/соседней папке `npx wxt@latest init speed-dial-wxt --template vue`, затем перенести файлы стартера в корень текущей `main`, сохранив `.git` и `SPEC.MD`; объединить `.gitignore`, а не терять его. Не переносить `node_modules`, `.output`, `.wxt` или временные артефакты.

## 2. Базовый технологический стек

**Обязательно:**

- WXT (официальный Vue-стартер, не самодельный Vite-конфиг).
- Vue 3 + Composition API + `<script setup lang="ts">`.
- TypeScript со строгими проверками по возможности стартера.
- Tailwind CSS **v4** с актуальным `@tailwindcss/vite` и `@import 'tailwindcss'`; собственные переменные/небольшой обычный CSS для сложных эффектов.
- **IndexedDB** для закладок, порядка, эскизов и при необходимости пользовательского фонового изображения. Допустим **Dexie** как единственная небольшая удобная обёртка; не заводи параллельные несовместимые хранилища одной сущности.
- **`wxt/utils/storage` / встроенный WXT Storage** в локальной области для небольших настроек. В манифесте `storage` permission.
- Манифест Chrome MV3; Firefox — версия по умолчанию, которую корректно поддерживает текущий WXT (на момент подготовки спецификации по умолчанию MV2). Firefox MV3 **не является дополнительным обязательным требованием**: важна реальная работа Firefox. Не подменяй корректную Firefox-сборку браузеронезависимым, но неверным манифестом.
- Только npm и зафиксированный **`package-lock.json`**; использовать `npm ci` для проверок.

**Не добавляй без необходимости:** Pinia (если достаточно `ref`/composables), Vue Router (нет множества маршрутов), Nuxt UI, shadcn, тяжёлые UI-киты, i18n, API-сервер, сервисы авторизации/синхронизации, сторонний drag-and-drop пакет (если нативный DnD надёжен), облачные сервисы для скриншотов. Не изобретай самописный state framework. Несколько небольших Vue-компонентов и сервисов достаточно.

Из официального Vue-стартера WXT **убери демонстрационные popup/content script**, если они не используются; создай **`entrypoints/newtab/index.html`** и **`entrypoints/background.ts`**. WXT автоматически создаёт `chrome_url_overrides.newtab` на основании entrypoint. Фон не должен импортировать UI или компоненты Vue.

## 3. Что именно есть в старом проекте: полный функциональный аудит

Исходные файлы `main` на начало миграции: `.gitignore`, `README.md`, `css/style.css`, `images/{icon16.png,icon48.png,icon128.png,newtab.png}`, `index.html`, `js/script.js`, `js/background.js`, `manifest.json`. В старом проекте **нет package.json, сборки, Vue или TypeScript**.

### 3.1 Манифест и страница

- Название: **SpeedDial X**.
- Русское описание: «При открытии новой вкладки вы увидите свои любимые сайты, и сможете перейти к ним в одно нажатие».
- `chrome_url_overrides.newtab = index.html`.
- Иконки 16, 48, 128 из `images/` — **сохранить оригинальные ресурсы**, если не требуется форматная адаптация к WXT.
- Фоновый `js/background.js`.
- `manifest_version: 3`, `permissions: ["unlimitedStorage"]`, `host_permissions: ["<all_urls>"]`.
- Новая реализация должна генерировать правильные браузерные манифесты из WXT-конфигурации, не поддерживать рядом второй исходный `manifest.json`.

### 3.2 Закладки и сетка (`js/script.js`)

Старое хранилище — Web SQL:

```sql
CREATE TABLE IF NOT EXISTS bookmarks (
  id INTEGER PRIMARY KEY ASC,
  url TEXT,
  title TEXT,
  favicon TEXT,
  thumbnail TEXT,
  position INTEGER
)
```

Операции: чтение всех в порядке `position`, чтение по `id`, вычисление `max(position)+1`, добавление, изменение `url/title`, удаление, очистка, обновление `position`, обновление `thumbnail`. Карточки — кликабельные ссылки с эскизом-фоном, favicon, заголовком, draggable; при наведении заголовок анимированно сдвигается. Есть опциональная карточка «+» для добавления сайта.

**Перенеси все действия**, включая порядок отображения, сохранение порядка после перезапуска, внешний вид карточек, обработку пустого списка, создание закладки без предварительного скриншота при ошибке захвата.

### 3.3 Модальные окна

- Добавить: поле URL, кнопка «Добавить».
- Изменить: скрытый ID, URL, заголовок, кнопка «Сохранить».
- Импортировать: textarea JSON + выбор локального файла + подтверждение импорта.
- Экспортировать: textarea JSON + кнопка сохранения `export.json`.
- Закрытие крестиком и щелчком по фону, анимации появления/исчезновения.
- Удаление одной закладки и удаление всех данных — диалог подтверждения (`confirm` приемлем, если UX не меняется принципиально).

**Важно:** закрытие окна во время асинхронной операции не должно создавать дубликатов и приводить к незаметной потере ошибки; кнопки занятых операций блокируются.

### 3.4 Контекстные меню

- Правая кнопка по пустому месту: **«Новая закладка», «Настройки»**.
- Правая кнопка по карточке: **«Открыть в новой вкладке», «Изменить», «Обновить эскиз», «Удалить»**.
- Меню позиционируется рядом с курсором, не выходит за видимую область; закрывается по клику вне/`Escape`.
- Операции должны применяться **строго к той карточке**, по которой открыто меню. Исключить старые гонки из `async get(id)` и общего `tab/id`.
- Стандартное браузерное контекстное меню в поле поиска не подменять.

### 3.5 Перетаскивание

- Drag-and-drop карточек внутри одной сетки, визуальный порядок сохраняется.
- Элемент «+» не участвует в перестановке.
- Сразу после drop сохраняется новый порядок в IndexedDB **одной согласованной операцией**, а не серией непроверенных независимых записей.
- Должны работать: перенос в начало, середину, конец; отмена drag; повторная сортировка после удаления или импорта; отсутствие дубликатов позиций.

### 3.6 Поиск Яндекса

- Поисковая форма сверху, текст «Поиск в Яндекс...», кнопка «Найти» неактивна при пустом вводе.
- Отправка запроса в Яндекс. Ранее использовался `https://www.yandex.ru/yandsearch` с параметром `text`; если этот URL больше не работает, используй текущий официальный URL поиска Яндекса с тем же результатом, а изменение объясни в отчёте.
- Подсказки по мере ввода с `https://suggest.yandex.ru/suggest-sl?part=...`; исходный код ожидает массив и подсказки в `data[1]`.
- Выбор подсказки мышью, стрелки **вверх/вниз**, Enter, фокус, закрытие/скрытие по уходу фокуса.
- Обновление подсказок при пустом запросе, отсутствии результата, сбоях сети и быстрых последовательных запросах должно быть корректным: `encodeURIComponent` / `URLSearchParams`, debounce, `AbortController` либо request token, очистка устаревших результатов, безопасный `textContent` / `{{ }}` (никакого `innerHTML` из сети).
- Проверить фактический CORS, формат API и доступность в Chrome/Firefox. Если сервис требует иных разрешений, явно задать **минимальные** host permissions. Не менять провайдера поиска.

### 3.7 Уведомления Mail.ru

- В настройках есть `email`.
- Если email заполнен — справа сверху отображается иконка письма (ссылка на `https://e.mail.ru/messages/inbox/`) и кружок с количеством непрочитанных сообщений при значении `> 0`.
- Старый код делает запрос:

```text
GET https://portal.mail.ru/NaviData?mac=1&Login=<email>
```

и ожидает `json.data.mail_cnt`.

- При пустом email иконка убирается. При нуле бейдж скрывается. При сбое сети не должно быть падения приложения и ложного счётчика.
- Функция **обязательно должна остаться**. Проверь доступность API и CORS на реальных сборках, авторизацию/куки и ограничения Firefox. Используй ровно необходимые permissions. Не храни пароль или токены, не добавляй OAuth/сервер без оснований. Не отправляй email на сторонние серверы, кроме выбранного пользователем сервиса Mail.ru.
- Старое поведение — проверка при загрузке/применении настроек, **без фоновых постоянных опросов**. Не добавляй polling самовольно.
- Если API объективно недоступно в текущих браузерах, **не имитируй успех**: реализуй корректное состояние ошибки, документируй результаты проверок и проведённые исследования. При возможности найди минимально инвазивный совместимый способ сохранить ту же функцию; не удаляй её ради успешной сборки.

- Сетка на широком экране подчиняется числу столбцов, ширине и отступам; на маленьком экране должна оставаться пригодной для использования. Старый CSS имеет медиа-запросы 768/1200/1600/1900 с 2/4/5/6 колонками, но inline-style из JS их перекрывал — перенеси **пользовательский результат**, а не эту ошибку; соблюдай выбранное число колонок на десктопе и не допускай горизонтального переполнения на мобильных размерах.
- **Исправь баг со строками booleans:** старое `localStorage` содержит `'true'`, `'false'`, `''` и прочие строки; проверять `Boolean('false')` нельзя. Корректно распарси при импорте и первом чтении, храни в новом слое настоящие `boolean`.
- **Исправь баг `setSettings`:** старый код вызывает `localStorage.clear()` при сохранении, из-за чего теряются отсутствующие поля и могут возникать несогласованности; новая реализация сохраняет валидные настройки без уничтожения других данных.

### 3.9 Создание скриншотов / favicon / title

Оригинальный `js/background.js` при `port` сообщении `{act:'thumbnail', url}`:

1. `chrome.tabs.create({url})` — открывает сайт отдельной вкладкой;
2. ждёт событие `tabs.onUpdated` с `status === 'complete'`;
3. вызывает `tabs.captureVisibleTab(null, {format:'png', quality:100})`;
4. возвращает `{url,title:changeTab.title,favicon:changeTab.favIconUrl,thumbnail:dataUrl}`;
5. закрывает созданную вкладку.

Старый `add()` ждёт эти данные, подставляет favicon с `favicon.yandex.net` при отсутствии, затем сохраняет закладку. Контекстное меню умеет обновлять только thumbnail.

**Это самый рискованный кроссбраузерный участок; нельзя механически копировать алгоритм.** `captureVisibleTab` делает снимок **активной**, а не произвольной вкладки. Нужно корректно выбирать окно и проверять, что активна именно временная вкладка целевого URL; учитывать ограничения прав, запретные схемы, тайм-ауты, невидимую/закрытую вкладку, ограничение частоты захватов, SPA/дозагрузку, гонки нескольких запросов и прекращение фонового service worker в MV3. Обязательна очистка событий/таймеров, `finally`-закрытие **только своей временной вкладки**, запрет закрытия любых пользовательских вкладок.

**Контракт операции:**

- Добавление закладки всегда начинается с валидного URL. Пустой URL, `javascript:`, `data:`, `file:` и внутренние схемы отклоняются с понятным сообщением. Ввод вроде `example.com` можно нормализовать в `https://example.com`; `http://` и `https://` сохранять.
- Захват происходит только по пользовательской операции добавления/обновления, с понятной индикацией того, что временно откроется сайт. Минимизируй влияние на текущую вкладку пользователя; если требование скриншота технически требует активации, не обманывай пользователя и не сохраняй скриншот чужой вкладки.
- Не допускать параллельных захватов, перепутанных ответов и утечек слушателей: очередь/мьютекс, request ID, timeout, обязательный cleanup. Соблюдай лимит браузерного API, не делай серию немедленных захватов.
- После успеха сохранять title, favicon и thumbnail. Заголовок, изменённый пользователем при редактировании, **не перезаписывать** при обновлении эскиза. Не перезаписывать прежний thumbnail при ошибке обновления.
- При невозможности захвата показывать ошибку/предупреждение и **предусмотреть сохранение закладки без эскиза** с заголовком по URL и доступным favicon/плейсхолдером. Не зависать навсегда из-за скриптов сайта, редиректов или недоступного домена.
- Выбирать приемлемый формат и размер изображений; не сохранять огромные base64-строки в WXT Storage. Предпочтительно хранить Blob в IndexedDB, освобождать созданные `objectURL` после использования. При желании пережимать/масштабировать скриншоты без заметного ущерба для интерфейса.
- Проверить наличие требуемых прав для `tabs`, `captureVisibleTab`, чтения `title/favIconUrl`, `<all_urls>` и host permissions **по сгенерированному манифесту каждого браузера**. Право `activeTab` само по себе не всегда подходит для автоматического открытия/захвата новой вкладки; нельзя считать его универсальной заменой `<all_urls>`.
- При невозможности обеспечить прежний автоматический захват с корректными разрешениями и безопасностью — не заявлять функциональный паритет, задокументировать точное ограничение и предложить проверенный альтернативный путь, не удаляя кнопку обновления.

### 3.10 Импорт/экспорт

Точный старый формат JSON:

```json
{
  "tabs": [
    {
      "id": 1,
      "url": "https://example.com",
      "title": "Example",
      "favicon": "https://example.com/favicon.ico",
      "thumbnail": "",
      "position": 1
    }
  ],
  "settings": {
    "width": "100",
    "countColumns": "6",
    "space": "24",
    "verticalCenter": "true",
    "addButton": "false",
    "background": "",
    "email": ""
  }
}
```

Эта структура иллюстративна; **в старых экспортированных JSON** могут отсутствовать некоторые ключи, быть разные значения полей и сохранённые data URL. Раньше `export()` **целенаправленно выставлял `thumbnail = ''`** для всех закладок; новый импорт должен нормально работать без эскизов и позволять обновить их позже.

Требования:

- Импорт из вставленного JSON **и** из файла; экспорт в видимый/копируемый JSON **и** скачивание `export.json`.
- **Обязательна обратная совместимость со старым форматом `tabs/settings`, включая строковые значения настроек.** Без потребности автоматически менять формат экспорта; предпочтительно оставить тот же top-level контракт и допустимые поля.
- Валидация структуры, типов, URL, разумных границ чисел, ID и позиций; сообщение об ошибке с указанием причины. Никакой вставки пользовательских значений через `innerHTML` и никакого выполнения JS из файла.
- Импорт **заменяет существующие закладки**, как в старом коде, но **только после предварительного подтверждения** с предупреждением о замене. Сначала полностью распарсить и проверить данные, потом изменять БД. При недействительном файле **ничего не удалять**.
- Учитывать возможные дубликаты/отсутствие `id`, пропуски и одинаковые `position`; сохранять правильный визуальный порядок без потери элементов, нормализовать позиции 1…N; сохранять заголовки, URL, favicon. Избегать двойной генерации записей/потери ID при повторном импорте.
- Замена набора закладок должна быть **одной IndexedDB-транзакцией**. Настройки находятся в другом хранилище: организовать snapshot/restore, staged update или другой явный порядок, чтобы сбой не оставлял непонятное полусостояние. Писать о восстановлении в коде и тестах; не обещать распределённую атомарность, которой нет.
- При экспорте не мутировать сохранённые объекты (`row.thumbnail = ''` в старом коде — потенциально опасный шаблон). Можно по старому контракту исключать тяжёлые эскизы, но **явно написать это в UI/README**. Пользовательский фон, если хранится отдельно как Blob, нужно включить в экспорт в совместимом с `settings.background` виде (или обеспечить равнозначное восстановление и описать формат).
- Упорядочить export по `position` и генерировать корректный UTF-8 JSON; очищать временные object URLs после скачивания.
- Импорт не должен автоматически открывать десятки сайтов для эскизов или вызывать захват экрана без команды пользователя.

### 3.11 Сброс данных

Кнопка «Удалить все данные» после явного подтверждения удаляет закладки, настройки, сохранённые эскизы, пользовательский фон и связанные данные расширения; состояние UI возвращается к значениям по умолчанию. Нельзя удалить данные других расширений, очистить браузерные закладки или повредить чужие вкладки.

## 4. Особый случай: устаревший Web SQL и перенос пользовательских данных

Это **неопциональное требование**.

`openDatabase('SpeedDial', ...)` использует Web SQL, который Chromium полностью удалил начиная с Chrome 119; Firefox Web SQL не поддерживал. **Нельзя обещать прямую автоматическую миграцию исторической Web SQL БД из современного браузера.** Не пытайся эмулировать `openDatabase` ради совместимости.

Нужны следующие безопасные сценарии:

1. **Старый JSON-экспорт — обязательный способ восстановления.** Реализовать совместимость и тест на реальном по структуре fixture старого экспорта.
2. Если пользователь обновляет **то же самое установленное расширение с тем же ID** и его старый `localStorage` ещё доступен, возможно прочитать настройки один раз при первой загрузке и перенести в WXT Storage, не очищая legacy-данные до подтверждения. Эта возможность зависит от сохранения extension origin/ID и фактического наличия данных. Реализовать разумную одноразовую миграцию настроек с маркером версии/успеха; не копировать бесконечно при каждом запуске.
3. Исторические **Web SQL-закладки** автоматически переносить **только если доказан реальный доступ к ним в целевой среде**; при отсутствии API не выдумывать восстановление. Нужна честная инструкция пользователю о восстановлении из `export.json` / старого доступного браузерного профиля.
4. Разница между установкой нового unpacked extension ID и обновлением расширения **с сохранением того же ID** должна быть отражена в README: хранилища и настройки двух разных extension ID автоматически не общие.
5. Не удалять/перезаписывать старый профиль или старые данные «для чистоты», не подсовывать синтетические данные в production.

Тесты должны отдельно покрывать отсутствие legacy-хранилища, старые строковые булевы значения, частично отсутствующие настройки, пустые `tabs`, устаревшие URL, невалидный JSON и невозможность прямой миграции Web SQL без потери данных.

## 5. Требования к UI и Tailwind

- **Сохрани узнаваемый дизайн** SpeedDial X на первом этапе: приглушённый серый фон по умолчанию, жёлтый акцент (`#fc0` и близкие оттенки), поиск сверху, сетка визуальных карточек с пропорциями примерно 16:9, контекстные меню, модальные окна, правая выдвижная панель настроек, фоновые изображения, плавные простые анимации.
- Цвета, размеры и поведение извлеки из `css/style.css`. Используй Tailwind v4 для layout/отступов/типографики/форм, CSS-переменные (`@theme` или `:root`) для токенов; обычный небольшой CSS допустим для сложных transition, backdrop и динамической grid-template.
- Не копируй слепо весь старый 678-строчный CSS и одновременно не переписывай весь дизайн «под современную библиотеку». Не вводи новую систему компонентов только ради модных эффектов.
- Сохранить изображения и значки из `images/`; добавить понятный fallback, если у сайта не получилось получить favicon/thumbnail. Не использовать сторонний сетевой CDN изображений для основного UI.
- Клавиатурная доступность: фокус, Enter/Space для операций на кнопках, Escape закрывает меню/диалоги, видимое состояние фокуса; семантические `button`, `a`, `dialog`/корректные роли. Не ломать контекстные меню мышью, drag-and-drop и поиск.
- Проверить читаемость и сетку на минимум **360×800**, **1280×800**, **1920×1080**; длинные заголовки не должны разрывать layout.
- Избегай XSS: URL проверять, строки выводить как текст, HTML из сайтов/импорта/подсказок не интерпретировать. Не включать `unsafe-eval` / отключать CSP для удобства разработки.

## 6. Архитектура данных и API

Предлагаемая модель (не буквальный обязательный интерфейс):

```ts
interface Bookmark {
  id: number
  url: string
  title: string
  favicon: string | null
  position: number
  // thumbnail: Blob | null — либо отдельное IndexedDB-хранилище по bookmarkId
}

interface SpeedDialSettings {
  width: number            // 50..100, default 100
  countColumns: number     // 2..12, default 6
  space: number            // 0..48, default 24
  verticalCenter: boolean  // default false
  addButton: boolean       // default false
  email: string            // default ''
  // background: отдельная ссылка/Blob или сериализуемая модель
}
```

- В IndexedDB операции CRUD, reorder и import должны иметь строгую типизацию и контролируемые транзакции.
- Во Vue хранить текущие реактивные данные, а не вручную пересоздавать элементы через `document.createElement` / `innerHTML` и каждый раз перевешивать обработчики.
- UI не знает подробностей IndexedDB; фон не знает подробностей Vue.
- Для запросов UI ↔ background использовать WXT/browser runtime messaging с типизированным контрактом; ошибка/timeout/cancel не должен оставлять Promise навечно и не должен утекать слушателями.
- `browser` API использовать через актуальные импорты WXT и с feature detection, где браузеры отличаются; не обращаться к браузерным API на верхнем уровне фонового entrypoint в Node-контексте построения WXT (инициализировать внутри `defineBackground`).
- При работе со скриншотами учитывать, что MV3 service worker временный; не полагаться на постоянно живое глобальное состояние для критичных данных. Сохранённые закладки и настройки переживают перезапуск воркера и браузера.
- Основной интерфейс **не должен ждать сети**, чтобы показать сохранённые карточки и поиск.

## 10. Правила принятия решений, если появляется неоднозначность

- **Сохраняй существующую функцию**, даже если API старый; сначала найди совместимую техническую реализацию и проверь её. «Легко удалить» — не аргумент.
- **Не придумывай успешные результаты** проверок Mail.ru, Яндекса, Firefox/Chrome, если реальный браузер/доступ к сервису недоступен.
- Когда внешний API невозможно проверить/использовать, реализуй правильное отображение ошибки и документируй конкретный блокер, при этом заверши всё остальное; не заменяй сервис другим без решения пользователя.
- Можно исправлять явные баги старого кода (Web SQL, `Boolean('false')`, опасный `innerHTML`, утечки слушателей, невалидный URL, потеря настроек, ошибки импортной транзакции, захват чужой вкладки). Не копируй ошибки ради «пиксельной совместимости».
- Можно улучшать надёжность/доступность UX, **не меняя набор функций и узнаваемый внешний вид**.
- Не реорганизуй Git вне рамок описанной схемы и не публикуй расширение.
- При наличии альтернативного решения выбирай **наименьшее читаемое** без лишних зависимостей и абстракций.
- Главное: **выполни полный перенос, а не только подготовку шаблона**. План этапов служит внутренним порядком работ, а не поводом останавливаться и спрашивать разрешение после каждого пункта.
